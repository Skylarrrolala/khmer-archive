## PostgreSQL 17 and administrative permissions

The files use ordinary transactional CREATE/ALTER/DROP POLICY, CREATE TABLE,
CREATE INDEX (not CONCURRENTLY), CREATE OR REPLACE FUNCTION, GRANT/REVOKE and
CREATE TRIGGER. PostgreSQL 17 supports the identity column, security-definer
functions, advisory locks, JSON/catalog queries and custom `KA00x` SQLSTATEs
used here. None of these migration files contains transaction control or
commands requiring execution outside a transaction. Earlier testing in this
session passed 476 assertions on PostgreSQL 17.11 using a simplified Supabase
stand-in; that does not validate hosted ownership or this new wrapper.

Native PostgreSQL requires ownership to change table policies. Supabase
Storage objects normally belong to `supabase_storage_admin`, not `postgres`.
Supabase's `supautils.policy_grants` can separately authorize the current
administrative role to CREATE/ALTER/DROP policies on `storage.objects`.
`MAINTAIN`, ordinary DML grants and BYPASSRLS alone are not policy-DDL authority.
Supautils is a loaded library and need not appear in `pg_extension`.

The wrapper requires effective ownership of `public.entries` and the existing
review function, public-schema privileges, Auth FK REFERENCES permission, and
either Storage ownership or an explicit policy-grant configuration. It also
requires unrestricted baseline reads so security-definer helper reads are not
silently limited by RLS. Configuration is only a preflight indication: the
actual DDL must still be accepted by the hosted server.

**Do not ALTER OWNER, SET ROLE to a managed service role, grant membership,
disable RLS, or change Supautils settings to make a check pass.** Stop and
review any mismatch. Managed Storage/Auth ownership must remain intact.

## Proposed execution sequence — not approved or executed yet

1. Confirm the intended production project and a fresh administrative
   connection, preferably as the dashboard's normal `postgres` role. This
   requires a database connection/SQL Editor, not an app API key. Do not paste
   credentials into the repo, journal, chat or shell history.
2. Run [the read-only checks](check-0004-0008.sql) and save the JSON result.
   Inspect policy expressions, function owner/grants, pending default, enum,
   bucket configuration, RLS flags and Storage ownership/configuration. All
   `row_security_active` flags must be false for this administrative check,
   while RLS itself stays enabled on the protected tables.
3. If its history-table field is non-null, also run the commented read-only
   version query in that file. Save those rows. Missing/empty history does
   not prove that migrations were not applied manually. Incomplete history
   needs review; it is not repaired by this script. Unexpected versions or
   any partial 0004–0008 objects are a stop condition.
4. After that baseline is reviewed and execution is explicitly approved,
   run [the complete dry-run](dry-run-0004-0008.sql) once, in one connection.
   It starts BEGIN, guards the 0003 baseline, reads the before-state, executes
   0004→0008, checks and reads the uncommitted after-state, then ends ROLLBACK.
   Do not run selected lines or replace ROLLBACK with COMMIT. If using psql,
   use `-X -v ON_ERROR_STOP=1 -f docs/dry-run-0004-0008.sql` with the connection
   configured separately. A client that displays only its last result may
   require exporting result sets to preserve the before/after evidence.
5. Run the same read-only checks again **after ROLLBACK**, using the same role.
   Compare with step 2, and repeat the history version query if applicable.
   The final database state should match the baseline: original policies,
   function definition hash/ACL/owner, bucket, entries, reviewers and photo
   metadata; all new functions/tables/sequence/trigger must be absent.
6. Report results and any errors. Permanent application, history updates,
   reviewer-account changes and app deployment require a different plan and
   approval; this file is not a permanent-rollout script.

If any statement fails, stop. In an interactive client that keeps the
connection open, send only ROLLBACK to end that transaction. Do not retry
individual statements. A closing/terminated connection also abandons its
uncommitted work. Read-only comparisons after a failure still matter.

## Risks and limits

- **Rollback does not mean zero disruption.** Policy/table DDL acquires real
  locks and may briefly block production reads, writes or uploads. Plan a
  quiet interval. Transaction-local bounds are 3 seconds waiting for each
  lock, 60 seconds per statement, 30 seconds idle in a transaction and 120
  seconds total after the version/preflight check. Timeouts can abort the
  trial or terminate its connection; they are not service-availability guarantees.
- No entry, account or Storage object is inserted, updated or deleted by
  the migration statements. Creating the history table does not backfill it.
  This dry-run deliberately does not invoke write RPCs, advance sequences,
  or run the test fixtures against production. Existing platform event
  triggers may run for DDL; inspect unexpected behavior rather than bypassing them.
- Before/during/after data digests can differ if users write concurrently.
  MD5 is only a compact change-detection aid here, not a security checksum.
  A SQL result cannot verify object-store bytes, Storage HTTP behavior or
  the Supabase Auth/API path; separate authenticated workflow checks remain.
- A successful rollback trial does not grant lasting review protections or
  upload limits. The app must not be deployed before the required permanent
  migration rollout. The public bucket still serves a known photo URL even
  when its entry is pending; 0005 restricts listing, not URL access.
- Metadata definitions are reported for human review. The preflight inventory
  guards do not prove every existing policy expression exactly matches Git.
  Do not treat version rows or policy names alone as proof of the baseline.
